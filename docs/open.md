# Open questions and roadmap

- Cooperative scheduling covers one interleaving: round-robin lockstep keeps warps in step, so `shared_exchange` likely passes even with BAR.SYNC as a no-op. Run cooperative kernels under adversarial schedules (warp-greedy until blocked, reverse, seeded random) and require identical results: that tests barrier enforcement and that fixture kernels are race-free. Timing proper matters only for racy code, fence-based ordering (memory model, not cycles) and scoreboards: the emulator completes instructions instantly, trusting control bits, and GPU fixtures keep the original controls on patched words, so a patched slot with longer or variable latency could read stale values on the GPU.
- Generic LD/ST (2026-10-15) model only the CTA's own shared window. On SM90+ the shared window may also hold distributed (cluster) shared memory, and ptxas builds the base from `SR_SWINHI` alone, so `SR_SWINSZ` and the rank layout there need hardware. Faults (window addresses beyond the allocation, unmapped global addresses) and 32-bit generic addresses are not modelled.
- LDG/LD `Pu` (2026-10-15) stays opaque. On SM89 hardware it read 0 in every run that completed, and it doesn't turn a fault into a flag. ptxas writes PT there on every path it was seen to take, so nothing it compiles uses `Pu`. Its only operand-driven encoders are in Mercury class 0xe6, whose creator is unknown (`research/ptxas/ptxas-finalizer-notes.md`, "LDG's Pu operand"). `Pnz` is modelled as zero-fill (`docs/hardware-facts.md`).
- Memory descriptors (2026-10-15): which range-form descriptors (bit 59) trap is unknown, so the runtime rejects them all. Value neutrality and the format were established only on SM89. The SM90+ default descriptors (`c[0x0][0x208]`, `0x358`) are unknown, and the emulator leaves them 0. ATOM/RED/LDGSTS descriptor forms have no family.
- Memory order inside one instruction (2026-10-16). `Outputs` computes every value, address and condition from the state before the instruction, then applies the register writes and then the stores in list order, so no load sees the same instruction's store. Instructions that would need that: a data write followed by an mbarrier read-modify-write (`STAS`, `REDAS`, `UTMALDG`), an overlapping `UBLKCP` (all reads first is memmove), and aliasing accesses of the dual-register (`Rd2`/`Rb2`) forms. If one is modelled, version memory rather than making `Outputs` an ordered statement list: `load(space, addr, w, after=k)` reads after the first `k` stores, and every existing load is `after=0`. Loads stay pure, so hash-consing, row merging, `narrow`/`specialize` and precompute stay sound, and register writes stay simultaneous; an ordered list would lose both and reorder every class's p-code.
- Trace the `-plr` liveness code that consumes connectors (start at the "Cannot %s as flow analysis is disabled" check, Ghidra 0x10a327).
- Parse md + latencies into a per-opcode table (operands, role, width, pipe, latency).
- Why nvdisasm prints some decodable instructions blank (GATHER, SCATTER, `__HIR*`, BPT.PAUSE, E6M9 immediates, SM75 HMMA .BF16/.TF32) and silently drops some modifier values (SM75 HMMA `altfmt=INVALID3`). Not a name table in the binary; never seen in real code.
- SLEIGH generation from `src/sass/decode/ir.py` (plan phase 3).
- Semantics roadmap, ordered by `src/sass/check/census.py` (2026-10-08; share = average fraction of all real-corpus instructions across SM75-SM120). After the control-flow fix: native 58-76% per arch, opaque 16-36%, primitive 6-8%.
  1. Done: control flow on every fallback branch; native SM90+ BRA.
  2. Done: cheap coverage (~10%): `URb`/`URc` operand names in IMAD/ISETP/IADD3/LEA emitters (~3.5%, ~7% on SM90); alias uniform/variant ops to existing emitters (UIADD3, UIMAD, USHF, ULEA, UISETP, ULOP3, USEL, UMOV, VIADD, IADD; ~3.5%); native PRMT (1.6%); FSEL (1.1%), FMNMX (0.6%, NaN/±0 rules).
  3. Done: native fp64 DFMA/DADD/DMUL and every DSETP comparison (~5%); DFMA via Ghidra's 16-byte float, where the double product is exact. DSETP MIN/MAX are totalOrder tests verified on SM89.
  4. Done: native packed fp16x2 HADD2/HFMA2 (~2%) with lane broadcasts/modifiers and SAT, including the `HFMA2.MMA Rd, -RZ, RZ, imm` constant move. FTZ/FMZ, alternate formats, RELU and other MMA forms stay opaque.
  5. Done: carry chains IADD3.X, LEA.HI.X, IMAD.X and ordinary predicate outputs (SM89 hardware-established; all-architecture emulator/dataflow checks).
  6. Kernel parameters as named constant-bank-0 variables in the decompiler (offsets/sizes from `.nv.info`, `src/sass/decode/cubin.py`).
  Stays primitive: SHFL, VOTE, BAR, BSSY/BSYNC, MUFU (hardware approximation; measured on SM89, modelling scoped in #21). Ghidra's emulator FloatFormat underflow bug (see below) could be reported upstream.
- SM107 semantics still inferred (2026-10-14; the rest has ptxas 13.4 / PTX 9.4 / cuda_fp8.hpp evidence, `docs/semantics.md`): Rd[31:16] of the scaled F2FP downconverts (taken as Rc[15:0]; ptxas passes 0), VISET's packed 16x2/8x4 lanes (ptxas only emits .S32/.U32), NaN results of FH*2's F16/BF16 outputs, and `.FTZ` of the F16x2-result FHADD2/FHMUL2 (PTX defines `.ftz` for half types generally, not in §9.7.5). Opaque: FH*2/FFMA2 `.FMZ`, `.NP` on broadcasts, UE5M3 upconverts, E8 downconvert. An SM107 GPU would settle all of them.
- LEPC's value (2026-10-14): CuLifter writes 0 and ptxas emits no LEPC for SM89 indirect calls (relocated MOV return addresses instead). One SM89 probe (`docs/hardware-facts.md`) gave the kernel's start if `c[0x2]` function pointers are absolute; an absolute anchor (a relocated code address, which our cubin loader doesn't apply) would settle it. LEPC stays opaque; `lepc__R_I_R`'s RSImm suggests an address relative to the next instruction, but plain LEPC's base is unknown.
- ELECT (SM90+) follows PTX `elect.sync` without hardware evidence; its `Pp` form and `.IGNOREKILL` are opaque.
- Ghidra tests in CI (2026-10-15). CI runs the coverage check and the Python tests on every architecture and lowering (`.github/workflows/ci.yml`), but not `pytest -m ghidra`. That needs Ghidra 12.1.4 with its pyghidra venv, and compiled languages: SM100+ compilers took 10-12 GiB of heap each, beyond a standard 16 GiB runner when several run at once. Options: build one language per matrix job (`sass-build-languages SMxx --fp F`, `--jobs 1`) and run `-m ghidra --arch SMxx --fp F` there; cache Ghidra's install and `.cache/` between runs; or a self-hosted runner.
- FTZ cost of native FMZ (2026-10-20). FMUL/FFMA `.FTZ` and `.FMZ` share one body (`select_in`), and FTZ forms execute about 9-17 more p-code operations than before FMZ was native (`ffma__RRR_RRR` 48 -> 65). Each factor's hoisted value table (`Lower.sel` -> `shared_subtrees` -> `value_table`) still recomputes the zero test, since a table can't reuse another's values, and FTZ forms evaluate the test and AND it with a decode-time 0. Testing the unflushed factors (done) removed the duplicated flushes (81 -> 65); testing the encoded factors would save one more op per form but made every language about 45 KB larger. The rest would need values shared by hoisted tables computed once in the parent into named temporaries before `build`ing the choice. That costs pseudo-register writes in p-code (check decompiler output), a write-before-build invariant (a stale read would see the previous instruction's value), and a `cost()` change ("a choice's arms can't reuse values") that shifts merging and sizes in every language; SM90 exact has about 181 KB of headroom.
